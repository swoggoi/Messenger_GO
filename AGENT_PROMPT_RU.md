# Задание для OpenCode: завершить интеграцию БипЧата с Go backend

Ты работаешь непосредственно в локальной копии репозитория `Messenger_GO`. В репозитории уже есть Go backend, PostgreSQL-схема, JWT-аутентификация, REST API, WebSocket hub и адаптивный frontend в `web/`.

**Нужно не написать план, а внести изменения в файлы проекта, выполнить сборку и тесты, исправить найденные ошибки и подготовить запуск на Windows 11.** Не переписывай проект с нуля и не заменяй Go/PostgreSQL на другой стек.

Фактический стек проекта: Go 1.25, PostgreSQL через `pgx/v5`, JWT через `golang-jwt/jwt/v5`, bcrypt, Redis, WebSocket через Gorilla WebSocket. В `go.mod` также есть Kafka-зависимость.

Не делай выводы о коде по именам файлов. Проверяй вызовы, реальные структуры JSON и SQL-запросы. Сохраняй существующие рабочие функции.

## 3. Учебные группы — строго пять значений

В `web/login.html` в регистрации уже добавлен обязательный select со следующими вариантами:

1. `Т-491`
2. `Т-492`
3. `Т-493`
4. `Т-494`
5. `Т-495`

Не добавляй старые варианты `ИС-21`, `ИС-22`, `ИС-31`, не добавляй вариант «Преподаватель» и не разрешай произвольный ввод.

В `web/app.js` уже есть клиентская проверка выбранной группы, а при регистрации отправляется поле `group_name`.

**Важно: сейчас в Go backend поле `group_name` не поддерживается и не сохраняется. Исправь это на backend и в PostgreSQL — нельзя оставлять поле формы, значение которого теряется.**

Требования к реализации:

- Добавь миграцию для учебных групп и связи пользователя с группой.
- Предпочтительный вариант: таблица `academic_groups` с уникальным `name`, плюс nullable `users.group_id` с внешним ключом. Существующие аккаунты не должны сломаться: у ранее созданных пользователей группа может оставаться `NULL`.
- Заполни таблицу ровно пятью значениями `Т-491`–`Т-495` через идемпотентный seed в миграции (`INSERT ... ON CONFLICT DO NOTHING`).
- Расширь `domain.RegisterRequest` полем `GroupName` с JSON-тегом `group_name`.
- При регистрации сервер обязан проверить, что передано одно из пяти допустимых значений и оно существует в `academic_groups`.
- Сохраняй `group_id` атомарно при создании пользователя. Не делай отдельную запись, при которой аккаунт может создаться без выбранной группы.
- Расширь `domain.User` безопасным публичным полем `group_name` (или согласованным DTO). Никогда не сериализуй `PasswordHash`.
- Возвращай `group_name` в `POST /auth/register`, `GET /users/me`, поиске пользователей и `GET /users/{userID}`, если это необходимо интерфейсу.
- При обновлении профиля не позволяй пользователю подменять учебную группу произвольной строкой. На этом этапе выбор группы выполняется при регистрации; менять её можно только отдельной явно реализованной операцией с серверной проверкой.
- Если группа не выбрана или отличается от списка, backend должен вернуть понятный JSON error и подходящий HTTP-статус.

Раздел «Группы» (`groups.html`) сейчас означает **групповые чаты**. Не смешивай академическую группу пользователя с групповым чатом. Если добавляешь автоматическое добавление пользователя в чат его учебной группы, сначала реализуй это осознанно и проверь, что это не создаёт повторные чаты/участников при повторном входе. Не создавай фиктивные групповые чаты.

## 4. Авторизация и регистрация

Текущая реализация находится в `internal/core/features/auth/`.

Что уже есть:

- `POST /api/v1/auth/register`;
- `POST /api/v1/auth/login`;
- `RegisterRequest` сейчас содержит `username`, `name`, `email`, `password`;
- `LoginRequest` сейчас принимает `email` и `password`;
- пароли хешируются через bcrypt;
- регистрация возвращает User, но не JWT;
- login возвращает `AuthResponse` с `token` и `user`;
- JWT подписывается HS256, срок жизни сейчас 30 дней;
- защищённые маршруты требуют `Authorization: Bearer <token>`.

Frontend после успешной регистрации выполняет login, чтобы получить JWT. Сохрани этот сценарий либо согласованно измени обе стороны.

Нужно:

1. Добавить поддержку входа как по email, так и по username. Сейчас `Service.Login` вызывает `FindByEmail`, поэтому текстовое поле «Почта или username» фактически не работает с username. Исправь repository/service. Сохрани совместимость JSON-контракта: можно передавать identifier в имеющееся поле `email`, если это не ломает текущих клиентов, либо согласованно обновить request и api.js.
2. Нормализовать email и username (trim; для поиска/уникальности — согласованный регистр).
3. Валидировать все обязательные поля на сервере: username, имя, email, пароль, учебную группу. Пароль — не менее 8 символов и хотя бы одна цифра, как в интерфейсе.
4. Проверять уникальность username и email. Возвращать понятное сообщение, отдельно не раскрывая внутренний SQL.
5. Оставить bcrypt. Никогда не хранить и не логировать пароль открытым текстом.
6. Обеспечить автоматический вход после регистрации через существующий последовательный вызов register → login.
7. Проверять токен на каждой защищённой операции. Не полагаться только на redirect в JavaScript.
8. При logout frontend должен очистить локальный токен и пользовательский кеш. Сейчас отдельного серверного endpoint отзыва JWT нет — не делай вид, что токен отозван на backend. Если добавляешь server-side logout, реализуй полноценную безопасную схему отзыва и тесты; иначе оставь локальный logout с честной семантикой.

## 5. Реальные контракты API и обязательная интеграция

В `cmd/messenger/main.go` сейчас используются **прямые маршруты на одном `http.ServeMux`**, например:

- `POST /api/v1/auth/register`;
- `POST /api/v1/auth/login`;
- `GET /ws`;
- `GET /api/v1/users/me`;
- `GET /api/v1/users/search`;
- `PUT /api/v1/users/profile`;
- `GET /api/v1/chats/`;
- `POST /api/v1/chats/private`;
- `POST /api/v1/chats/group`;
- `GET /api/v1/chats/{chatID}`;
- `GET /api/v1/chats/{chatID}/messages`;
- `POST /api/v1/chats/{chatID}/messages`;
- `POST /api/v1/chats/{chatID}/read`;
- `POST /api/v1/upload/avatar`.

**Не переписывай это описание как будто в `main.go` уже есть вложенные submux или обязательный `StripPrefix`: в предоставленной версии маршруты зарегистрированы напрямую.** Проверь фактическое поведение Go `ServeMux` и меняй только то, что реально требуется.

### Пользователи

Сейчас существуют:

- `GET /api/v1/users/me` — текущий пользователь;
- `GET /api/v1/users/search?q=...` — поиск по username, имени или email;
- `PUT /api/v1/users/profile` — обновление name, username, email, avatar_url.

Добавь защищённый маршрут:

- `GET /api/v1/users/{userID}` — безопасные публичные поля пользователя для восстановления названия личного чата.

Проверь UUID, возвращай 404 для неизвестного пользователя, не возвращай `password_hash` и другие внутренние поля. Исключи текущего пользователя из результатов контактов, если это требуется интерфейсом.

### Чаты

Сейчас есть:

- `GET /api/v1/chats/`;
- `POST /api/v1/chats/private` с `{ "user_id": "UUID" }`;
- `POST /api/v1/chats/group` с `{ "name": "...", "user_ids": ["UUID"] }`;
- `GET /api/v1/chats/{chatID}`.

В домене есть `Chat`, `ChatMember`, `ChatListItem`. В `chats/service.go` уже существует `GetMyChats`, возвращающий `[]domain.ChatListItem`, а в `chats/handler.go` обработчик `GetMyChats` в текущем состоянии вызывает `GetChats` и возвращает `[]domain.Chat` с `members`.

Это несоответствие нужно разрешить. Для списка чатов интерфейсу нужны стабильные поля:

- `id`;
- `type` (`private`, `group`, `saved`);
- `name`;
- `partner_id` для личного чата, если есть;
- `last_message`;
- `last_message_time`;
- `last_sender_id`;
- `unread_count`;
- `created_at`.

Используй существующий DTO `ChatListItem` и существующий repository query, если они корректны. Исправь handler/service так, чтобы реальный JSON точно совпадал с `web/app.js`. Проверь личный чат после перезапуска и корректное имя собеседника.

Проверь, что:

- личный чат создаётся/переиспользуется без дубликатов;
- нельзя создать личный чат с самим собой;
- пользователь может читать только свои чаты;
- пользователь не может добавить участника в чужой чат;
- операции с участниками доступны только owner/admin;
- групповой чат не смешивается с академической группой.

### Сообщения

Существуют:

- `GET /api/v1/chats/{chatID}/messages?limit=50&offset=0`;
- `POST /api/v1/chats/{chatID}/messages` с `{ "content": "..." }`;
- `POST /api/v1/chats/{chatID}/read`.

В `domain.Message` / JSON интерфейс ожидает `id`, `chat_id`, `sender_id`, `sender_name`, `content`, `status`, `created_at`.

Особенно внимательно проверь безопасность: `CreateMessage` уже проверяет членство отправителя в чате, но `GetMessages` в текущем handler/service вызывает выборку истории без явной проверки, что текущий пользователь является участником. Исправь это. Любое чтение, отправка и отметка прочтения должны проверять членство.

Убедись, что `sender_name` действительно заполняется запросом репозитория, а не остаётся пустым. Пагинация должна ограничивать допустимый `limit` сверху и корректно обрабатывать `offset`.

На frontend:

- загружай сообщения из API;
- отправляй сообщения на сервер;
- очищай поле только после успешной отправки;
- при ошибке не теряй набранный текст;
- после обновления страницы восстанавливай список и историю;
- корректно обрабатывай пустой чат и сетевые ошибки.

### WebSocket и polling

Backend содержит WebSocket endpoint `/ws?token=...`, Hub проверяет JWT и отправляет события, в `messages.Service` настроен `BroadcastToUsers`. Текущий frontend использует polling примерно раз в 4 секунды.

Проверь реальный формат `domain.WSEvent` и payload. Предпочтительно подключить WebSocket в frontend и обновлять только активный чат по событию `new_message`. Оставь polling как fallback при недоступном WebSocket. Не допускай дублирования одного сообщения при одновременном событии WS и ответе POST.

Проверь origin-политику WebSocket и CORS. Сейчас WebSocket `CheckOrigin` разрешает любой origin, а CORS ставит `Access-Control-Allow-Origin: *`. Для приложения с JWT это нужно ограничить same-origin или явно настроенными адресами, если кросс-доменный режим действительно нужен.

## 9. Конфигурация и запуск на Windows 11

В `config.NewConfigMust()` используются:

- `PORT`;
- `DB_SOURCE`;
- `JWT_SECRET`;
- `REDIS_ADDR`;
- `REDIS_PASSWORD`;
- `REDIS_DB`;
- `KAFKA_BROKERS`;
- `KAFKA_TOPIC`.

В текущем `docker-compose.yaml` PostgreSQL создаётся с:

- user: `messenger`;
- password: `messenger_pass`;
- database: `messenger_db`;
- порт на хосте: `5432`.

Для Go-процесса, запускаемого на Windows-хосте, DSN будет использовать `localhost:5432`. Для контейнера приложения — имя сервиса `postgres:5432`. Не смешивай эти два режима.

Сейчас `main.go` создаёт `messages.Service` с `nil` Kafka writer, поэтому Kafka фактически не участвует в отправке сообщений в текущей точке запуска. Redis используется для online presence как дополнительный компонент. Не делай неиспользуемый Kafka обязательным условием локального теста переписки. Сначала обеспечь рабочий минимум: Go + PostgreSQL; Redis можно запускать через compose как optional-зависимость для online presence.

Подготовь:

- `.env.example` без реальных секретов;
- `start.bat` для Windows 11;
- `README.md` с точными шагами.

`start.bat` должен:

1. Проверять наличие Go нужной версии и Docker Desktop, если выбран запуск PostgreSQL через Docker.
2. При первом запуске создавать `.env` из `.env.example`, не перезаписывая уже существующий `.env`.
3. Запускать необходимые инфраструктурные службы через Docker Compose (как минимум PostgreSQL; Redis — если требуется текущей конфигурации).
4. Дожидаться готовности PostgreSQL, а не просто делать короткий `timeout`.
5. Применять миграции безопасно и повторяемо.
6. Запускать backend из корня репозитория.
7. Выводить адрес `http://localhost:8080`.
8. Не требовать отдельного ручного запуска frontend-сервера.

Если Docker Desktop недоступен, README должен честно описывать альтернативу с уже установленным PostgreSQL. Не заявляй, что приложение запустилось, если команда завершилась ошибкой.

В ZIP нет реального `.env`. Не создавай и не коммить реальные пароли/JWT secrets. Не выводи секреты в логи.

## 11. Ручной сценарий приёмки

После запуска приложения:

1. Открыть `http://localhost:8080`.
2. Зарегистрировать первый аккаунт с группой `Т-491`.
3. Проверить, что `group_name` сохранён в PostgreSQL и возвращается в профиле.
4. Выйти и снова войти по email.
5. Выйти и войти по username.
6. Создать второй аккаунт, например с группой `Т-492`, в другом браузере/профиле.
7. Найти второго пользователя через «Контакты».
8. Создать/открыть личный чат.
9. Отправить сообщение в обе стороны.
10. Обновить обе страницы и убедиться, что история сохранилась.
11. Проверить, что третий неучастник не может читать чужую переписку через подстановку UUID.
12. Проверить мобильный интерфейс и переключение списка чатов/переписки.

## 12. Что считать завершением

Работа не закончена после создания файлов или описания плана. Заверши интеграцию на уровне кода.

В финальном отчёте укажи:

- какие файлы изменены/добавлены;
- какие миграции добавлены и как их применить;
- точную команду запуска на Windows;
- фактические результаты `go test`, `go vet`, `go build`;
- какие сценарии ручной проверки удалось выполнить;
- что осталось нереализованным (например, общий обмен файлами), если такое осталось.

Не добавляй тестовые аккаунты, демо-режим, фиктивные чаты и фальшивые подтверждения действий.
